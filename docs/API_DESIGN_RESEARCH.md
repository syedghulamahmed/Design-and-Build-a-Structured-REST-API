# API Design Research

## Stripe conventions adopted

Stripe documents a REST-oriented API with predictable resource URLs, JSON responses, standard HTTP verbs/status codes, and explicit error types. Its API reference also documents idempotency keys for safely retrying mutating requests and pagination for large collections.

1. **Resource-oriented URLs:** TalentBridge uses `/internships`, `/internships/:id`, `/applications/:id` rather than action names such as `/createInternship`.
2. **HTTP status discipline:** successful creates return `201`, deletes return `204`, missing resources return `404`, validation returns `422`, and business conflicts return `409`.
3. **Idempotent retries:** POST endpoints accept `Idempotency-Key`; repeated requests with the same key and request fingerprint replay the original successful response instead of creating a second resource.
4. **Pagination:** `GET /internships` uses explicit `page`, `limit`, filtering, and sorting parameters.

Sources: [Stripe API Reference](https://docs.stripe.com/api) and [Stripe Errors](https://docs.stripe.com/api/errors).

## RFC 9457 comparison

RFC 9457 defines a standard Problem Details object with members such as `type`, `title`, `status`, `detail`, and `instance`, using `application/problem+json`. TalentBridge deliberately keeps the assignment's required envelope `{ error: { code, message, details? } }` because it is the contract requested by the task. The design is conceptually similar: `code` identifies the machine-readable problem, `message` gives the human-readable explanation, and `details` carries structured validation/business information. A future version could expose RFC 9457 fields directly or negotiate `application/problem+json` without changing service-layer business logic.

Source: [RFC 9457 — Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html).

## Status-code scope

The assignment lists `401 Unauthorized` and `403 Forbidden` among HTTP statuses to understand. This Task 3 API intentionally has no authentication/authorization layer, so those responses are not generated by the current contract. They become relevant when protected company/student operations are introduced in a later task.
